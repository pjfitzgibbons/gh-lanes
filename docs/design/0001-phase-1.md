# Design 0001 — Tracker, Phase 1 (CLI only)

**Implements:** [ADR 0002](../adr/0002-bespoke-tracker-architecture.md) Phase 1 · **Requirements:**

## Repo question: the tool is its own repo, the data is not

These are two different things and they belong in different places.

| | Where | Why |
|---|---|---|
| **The tool** — CLI, schema, index, templates | **its own repo** | It is a general-purpose tool with no Contoso content. It has its own tests, versioning and release cycle, and a reader could install it without this project |
| **The data** — `.tracker/items/*.yml`, `config.yml` | **`ms-security-docs`** (the hub) | It is planning data for *this* project and belongs beside `PLAN.md`. It is the evidence `G1` is about |

Keeping the tool here would put a Python application in a repo whose stated contents are "plan, blog
drafts, ADRs, compliance matrix, runbooks", and would make one of the four tracked repos privileged
over the others for no reason.

**Costs of a fifth repo, stated plainly:** `settings.json` does **not** inherit, so it
needs its own copy plus a copy of the attribution hook — the verified config-resolution rule from
Act 0.3. Call it 2 points of setup. It also gets its own issue tracker, which is the dogfooding
opportunity: **the tracker's own backlog is the first thing it tracks.**

**Decided 2026-10-10: the repo is `gh-lanes`, the product is GH Lanes, the CLI command is `lanes`.**
`gh-lanes` is free on both GitHub and PyPI — plain `lanes` is already taken on PyPI, which would
matter if this is ever published. The `gh-*` prefix states what it integrates with, which is the
discovery half of PLAN.md's repo-naming rule, and it leaves the door open to shipping as a real
`gh` extension later since the tool already shells out to `gh` exclusively. Not part of the Contoso
fiction, so the naming framework's fiction half does not apply.

**This document lives here until that repo exists, then moves with the code.**

## Phase 1 scope

**In:** item schema and validation · cycle detection · SQLite index · `gh` pull · reconcile ·
`next` / `ready` / `why` / `board` / `list` / `show` / `status` · `set` / `new` / `ice` /
`schedule` · `freeze` · `mirror` · `validate` · `reindex` · `--json` everywhere.

**Out:** HTML rendering, the web server, drag interaction, transfer handling, `push-drafts`.
Deferred to Phases 2 and 3.

**Acceptance criterion:** `lanes next` is good enough to work from daily. If it is not, Phase 1
failed and Phase 2 is mandatory rather than optional.

## Layout

```
gh-lanes/
  pyproject.toml            # uv, python >=3.14
  src/ghlanes/
    __init__.py
    cli.py                  # Typer app — thin; every command delegates to core
    config.py               # config.yml model + discovery
    model.py                # Item, Milestone — pydantic v2
    store.py                # read/write .tracker/items/*.yml (ruamel, comment-preserving)
    index.py                # SQLite build + query
    gh.py                   # every subprocess call to gh, in one place
    git.py                  # every subprocess call to git, in one place
    validate.py             # the rule set, one function per rule
    plan.py                 # duration, schedule, lane heads, next/ready/why
    reconcile.py            # issue <-> item membership
  tests/
    test_validate.py  test_plan.py  test_store.py  test_reconcile.py
    fixtures/                 # a committed .tracker/ tree
```

**Rule: `gh.py` and `git.py` are the only modules that spawn a process.** Everything else is pure
and unit-testable against fixtures, which is what makes `plan.py` — the part with the real logic —
testable without a network or a repo.

## Discovery

`.tracker/` is found by walking up from `cwd`, like git. `LANES_ROOT` overrides. If none is found,
exit 2 with the path searched.

## Data model

```python
# model.py
Estimate = Literal[1, 2, 3, 5]          # 8 and 13 are rejected, not representable
Priority = Literal["P0", "P1", "P2", "P3"]
Status   = Literal["Icebox", "Todo", "In Progress", "Blocked", "Done"]

class Baseline(BaseModel):
    start: date
    finish: date
    frozen_at: datetime
    reason: str

class Item(BaseModel):
    node_id: str                         # GitHub global id. The real key
    issue: int | None = None             # human key; cache. None while draft
    repo: str                            # short name, must be in config.repos
    draft: bool = False
    estimate: Estimate | None = None     # None = needs-triage, or a parent with children
    priority: Priority = "P2"
    status: Status = "Icebox"             # tracker-owned: GitHub has only open/closed
    ordinal: int | None = None            # writable rank, sparse (100, 200...). Tiebreak in `next`
    lane: str | None = None              # must be in config.lanes
    milestone: str | None = None         # None <=> Icebox
    depends_on: list[int] = []
    baseline: Baseline | None = None
```

Absent on purpose: title, state, labels, assignee, **parent**. All GitHub-owned, read through
`gh`, cached in the index, never written to a file.

## Index

Rebuilt wholesale, never incrementally — 60 items makes cleverness unjustifiable.

```sql
CREATE TABLE meta       (key TEXT PRIMARY KEY, value TEXT);          -- fetched_at, schema
CREATE TABLE gh_issue   (node_id TEXT PRIMARY KEY, number INT, repo TEXT, title TEXT,
                         state TEXT, closed_at TEXT, parent_node_id TEXT,
                         sub_total INT, sub_completed INT);
CREATE TABLE gh_label   (node_id TEXT, label TEXT);
CREATE TABLE item       (node_id TEXT PRIMARY KEY, issue INT, repo TEXT, draft INT,
                         estimate INT, priority TEXT, lane TEXT, milestone TEXT,
                         baseline_start TEXT, baseline_finish TEXT, path TEXT);
CREATE TABLE dep        (node_id TEXT, depends_on_issue INT);
CREATE VIEW  v_work AS   -- the join every command reads
  SELECT i.*, g.number, g.title, g.state, g.closed_at, g.parent_node_id,
         g.sub_total, g.sub_completed
  FROM item i LEFT JOIN gh_issue g USING (node_id);
```

## Validation rules

`validate.py` — one function per rule, each returning zero or more findings. Exit 1 if any
`ERROR`.

| Rule | Level | Message |
|---|---|---|
| estimate in {1,2,3,5} | ERROR | `#N estimate 8 is a refusal code, not a size — split it` |
| parent with children has no estimate | ERROR | `#N has N children and an estimate; roll-up would double-count` |
| `lane` in `config.lanes` | ERROR | `#N lane 'x' is not configured` |
| `depends_on` entries resolve | ERROR | `#N depends on #M, which is not an open issue` |
| no self-dependency | ERROR | `#N depends on itself` |
| **no dependency cycle** | ERROR | `cycle: #A -> #B -> #A` |
| `depends_on` is intra-milestone | WARN | `#N depends on #M in a different milestone; milestone order already implies it` |
| milestone absent ⟺ status Icebox | ERROR | `#N has no milestone but is not Icebox` |
| `status` in `config.statuses` | ERROR | `#N status 'x' is not configured` |
| status Done ⟺ issue closed | ERROR | `#N is Done but issue #N is open` |
| stored Blocked agrees with deps | WARN | `#N is Blocked but all dependencies are met` |
| `ordinal` unique within a lane | WARN | `#N and #M share ordinal 200 in lane L` |
| every open issue has an item | ERROR | `#N is not tracked — run reconcile` |
| item resolves to a live issue | ERROR | `#N is an orphan (node_id does not resolve)` |
| title `[N]` matches estimate | WARN | `#N title says 3, estimate is 2 — run mirror` |
| estimate and lane present | WARN | `#N needs triage` |
| baseline frozen for a closed milestone | WARN | — |

## `next` / `ready` / `why`

```python
def candidates(items):                       # plan.py
    return [i for i in items
            if i.status not in ("Done", "Icebox")
            and i.estimate is not None                    # needs-triage excluded
            and all(d in closed for d in i.depends_on)]

def lane_head(lane_items):
    return sorted(lane_items, key=sort_key)[0]

def sort_key(i):
    return (PRIORITY_ORDER[i.priority], i.ordinal if i.ordinal is not None else 10_000 + i.number, i.number)
```

- **`next`** — `candidates` ∩ lane heads, sorted, take the first. One line, plus duration and what
  it unblocks.
- **`ready`** — one row per lane: the head, its estimate, and unmet blockers.
- **`why N`** — the negation. Report every reason in order: not estimated · iced · done · unmet
  dependency (with each) · not the lane head (naming the head).

`duration_days = max(1, ceil(estimate / points_per_week * 7))`. Elapsed calendar time; **no
weekend exclusion** — the idle days are already inside the rate.

## GitHub and git interaction

Every call lives in `gh.py` / `git.py`. The complete Phase 1 set:

| Purpose | Call |
|---|---|
| Pull issues | `gh issue list --repo R --state all --limit 500 --json number,id,title,state,closedAt,labels` |
| Pull parentage | `gh api graphql` over `Issue.parent` / `subIssuesSummary`, batched per repo |
| Create | `gh issue create --repo R --title "[N] T" [--parent P]` |
| Mirror | `gh issue edit N --repo R --title "[N] T"` |
| Actual finish | from `closedAt` in the pull — no extra call |
| Rate limits | one `gh issue list` per repo per pull. **Never per-item writes in a loop** — the lesson from the lane batch failure |

## Testing

- `validate.py` and `plan.py` are pure: fixtures in, findings out. **Cycle detection and
  `next` selection get a case each per branch** — these are the two places a bug is silent.
- `gh.py` and `git.py` are mocked by a recorded-output fixture; no network in the suite.
- One end-to-end test over the committed fixture tree asserting `validate` exits 0 and `next`
  returns the expected issue.

## Resolved 2026-10-10

1. **`status` is tracker-owned and stored.** GitHub has only open/closed, so `Todo` /
   `In Progress` / `Blocked` have nowhere else to live. It joins the tracker-owned column in the
   ADR's ownership table. `Done` and `Icebox` remain *derivable* and are cross-checked by
   `validate`: `Done` must agree with the issue being closed, and `Icebox` must agree with milestone
   absence. So the stored value is asserted but not unchecked.
2. **`ordinal` is adopted**, under the key `ordinal` in the item YAML. A writable integer, sparse by
   convention (100, 200, 300…) so an item can be inserted without renumbering. It is the **tiebreak
   inside a priority band**, not a replacement for priority — the lesson from trying a bare rank
   earlier was that an opaque integer carries no intent, while a band plus a tiebreak carries both.

## Open questions

1. Does `reconcile` auto-create item files, or only report? Leaning: report by default, create on
   `--apply`.
2. **Where do `Blocked` and `In Progress` come from in Phase 1?** Both are *derivable* — `Blocked`
   from unmet dependencies, `In Progress` from a branch existing — and derived beats typed. But
   branch detection is Phase 3, so Phase 1 stores them and `validate` warns when a stored `Blocked`
   disagrees with the dependency graph.
