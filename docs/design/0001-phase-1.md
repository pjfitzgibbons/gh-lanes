# Design 0001: Tracker, Phase 1 (CLI only)

**Implements:** Phase 1 of the [architecture](../architecture.md) · **Requirements:**
[requirements.md](../requirements.md) · **Status:** draft

<a id="naming"></a>
## 1. Naming

The tool lives in its own repo, and `.tracker/` lives in whichever repo is being planned
([ADR 0002](../adr/0002-tracker-per-repo.md)).

The tool's repo carries its own Claude Code settings and attribution hook, because that
configuration does not inherit from directories outside the repo. Its own issues are the first
backlog it tracks.

The repo is `gh-plan`, the product is GH Plan, and the CLI command is `plan`. `gh-plan` is free
on both GitHub and PyPI. Plain `plan` is taken on PyPI, so the package is `gh-plan` and installs
the `plan` command. The `gh-` prefix is what a `gh` extension needs: installed as one, the tool
runs as `gh plan`. It already shells out to `gh` for everything it reads and writes.

<a id="scope"></a>
## 2. Scope

**In:** item schema and validation · cycle detection · SQLite index · `gh` pull · reconcile ·
`next` / `ready` / `why` / `board` / `list` / `show` / `status` · `set` / `new` (without `--draft`) /
`ice` / `schedule` · `freeze` · `mirror` · `validate` · `reindex` · `--json` everywhere.

**Out:** HTML rendering, the web server, drag interaction, transfer handling, `push-drafts`.
Deferred to Phases 2 and 3.

**Acceptance criterion:** Phase 1 ships no HTML and no server, so the terminal has to answer *what
do I do now* well enough to work from. `plan next` (§8.3) is that answer. If it is not good enough
to work from daily, Phase 1 failed and the HTML views of Phase 2 are mandatory.

<a id="phasing"></a>
## 3. Phasing

Each phase is useful on its own.

| Phase | Contents | Standing value if we stop here |
|---|---|---|
| 1: CLI only, terminal views | schema, validation, cycle detection, pull, reconcile, title mirror, index, `next` / `ready` / `why` / `board`, plus repo setup and tests | Already beats Projects v2: real dependencies, cycle detection, server-side split rule, baselines, evidence in git, no rate limits, and a usable *what-next* answer |
| 2: HTML views | HTML templates, CSS Grid board and timeline, SVG dependency arrows, `plan render` → `.tracker/out/`, then `plan serve` serving the same templates | The board and the dependency arrows |
| 3: write UI + sync | drag, transfer handling, offline drafts (`new --draft`, `push-drafts`) | Full replacement |

HTML rendering sits in Phase 2. Phase 1 answers *what next* in the terminal instead (§8.3). Charts
are a presentation upgrade, because every fact a chart would show is already in the index by the
end of Phase 1. The templates and the server land together in Phase 2, since serving an existing
template is nearly free once it exists.

Within Phase 1, reconcile is built before create: reconcile alone makes the system tolerant of
every creation route ([architecture §8](../architecture.md#creation-paths)).

Phase 1 clears more MUSTs than any tool in the survey, including the three that none satisfied.
Phases 2 and 3 are convenience and can be judged later, on evidence.

<a id="layout"></a>
## 4. Layout

```
gh-plan/
  pyproject.toml            # uv, python >=3.14
  src/ghplan/
    __init__.py
    cli.py                  # Typer app — thin; every command delegates to core
    config.py               # config.yml model + discovery
    model.py                # Item, Milestone — pydantic v2
    store.py                # read/write .tracker/items/<repo>/*.yml (ruamel, comment-preserving)
    index.py                # SQLite build + query
    gh.py                   # every subprocess call to gh, in one place
    git.py                  # every subprocess call to git, in one place
    validate.py             # the rule set, one function per rule
    plan.py                 # duration, schedule, lane heads, next/ready/why
    reconcile.py            # issue <-> item membership
  tests/
    test_validate.py  test_plan.py  test_store.py  test_reconcile.py
    fixtures/                 # a committed .tracker/ tree
```

**Rule: `gh.py` and `git.py` are the only modules that spawn a process.** The `timekeeping/`
adapters of [design 0002](0002-tracked-time.md) are the one other exception. Everything else is pure
and unit-testable against fixtures, which is what makes `plan.py`, the part with the real logic,
testable without a network or a repo.

<a id="discovery"></a>
## 5. Discovery

`.tracker/` is found by walking up from `cwd`, like git: the nearest directory holding `.tracker/config.yml` is the root. `PLAN_ROOT` names that directory and skips the walk. If none is found, exit 2, naming every path searched. Repo paths in `config.repos` are relative to the root.

<a id="data-model"></a>
## 6. Data model

<a id="item"></a>
### 6.1 Item

```python
# model.py
Estimate = Literal[1, 2, 3, 5]          # 8 and 13 are rejected, not representable
Priority = Literal["P0", "P1", "P2", "P3"]
Status   = Literal["Icebox", "Todo", "In Progress", "Blocked", "Done"]

class Baseline(BaseModel):
    start: date
    finish: date
    frozen_at: datetime
    reason: str

class Item(BaseModel):
    node_id: str                         # GitHub global id. The real key
    issue: int | None = None             # human key; cache. None while draft
    repo: str                            # short name, must be in config.repos
    draft: bool = False
    estimate: Estimate | None = None     # None = needs-triage, or a parent with children
    priority: Priority = "P2"
    status: Status = "Icebox"             # tracker-owned: GitHub has only open/closed
    ordinal: int | None = None            # writable rank, sparse (100, 200...). Tiebreak in `next`
    lane: str | None = None              # must be in config.lanes
    milestone: str | None = None         # None <=> Icebox
    baseline: Baseline | None = None
```

An item file:

```yaml
# .tracker/items/web-app/23.yml
issue: 23                # human join key — CHANGES on repo transfer
node_id: I_kwDOA1b2c3    # GitHub global id — SURVIVES transfer. The real key
# draft: true            # set only before the GitHub issue exists (offline create)
repo: web-app
estimate: 2              # 1 2 3 5 only — 8/13 rejected at write time
priority: P0
status: Todo             # tracker-owned; Done/Icebox cross-checked by validate
ordinal: 100             # sparse rank — tiebreak within a priority band
lane: frontend           # single-valued by schema
milestone: beta          # our milestone, which may span repos
baseline:
  start: 2026-10-13      # written once by `plan freeze beta`
  finish: 2026-10-15
  frozen_at: 2026-10-10T16:00:00Z
  reason: "Beta checkpoint"
```

Absent on purpose: title, body, state, labels, assignee, parent and dependencies (blocked-by). All are GitHub-owned, read
through `gh` and cached in the index, so no file holds a copy that would need reconciling.

<a id="identity"></a>
### 6.2 Identity

An issue number is not stable, because `gh issue transfer` changes it. The schema therefore carries
`node_id` (GitHub's global id, stable across transfer) as the real key, and keeps `issue:` as the
human-readable key, treated as a cache. Reconcile repairs a stale `issue:` from `node_id` rather
than reporting a false orphan.

The file lives at `.tracker/items/<repo>/<n>.yml`, where `<repo>` is the short name in
`config.repos`. The repo is part of the path because two repos can share an issue number. When a
transfer changes `issue:` or `repo:`, reconcile renames the file to match. Commands accept `23` when
only one configured repo has a #23, and `web-app#23` otherwise; an ambiguous bare number is an
error that lists the candidates.

<a id="status"></a>
### 6.3 Status

`status` is tracker-owned ([architecture §3.2](../architecture.md#tracker-owned)) and stored.
GitHub has only open/closed, so `Todo` / `In Progress` / `Blocked` have nowhere else to live.
`Done` and `Icebox` remain *derivable* and are cross-checked by `validate`: `Done` must agree with
the issue being closed, and `Icebox` must agree with milestone absence.

Reconcile keeps `Done` in step with GitHub. When a pull shows an issue closed and its item is not
`Done`, reconcile sets `status: Done`; like every reconcile write, it is dry by default and written
with `--apply`. An item marked `Done` whose issue has been reopened is reported and left unchanged,
because the status it had before closing is not recorded.

`Blocked` and `In Progress` are derivable too: `Blocked` from the issue being blocked by an open
issue, and `In Progress` from a branch existing. Branch detection is Phase 3 (#42, #45), so Phase 1
stores both, and `validate` warns when a stored `Blocked` disagrees with the blocked-by edges in the
index.

<a id="ordinal"></a>
### 6.4 Ordinal

`ordinal` is a writable integer in the item YAML, sparse by convention (100, 200, 300…) so an item
can be inserted without renumbering. It is the tiebreak inside a priority band, not a replacement
for priority: an opaque integer carries no intent, while a band plus a tiebreak carries both.

<a id="milestones"></a>
### 6.5 Milestones

One file per milestone, at `.tracker/milestones/<id>.yml`, for the same reason there is one file
per item: concurrent edits to different milestones merge cleanly and `git log -p` on one file is
that milestone's history. There is no `milestones_file` key; milestones are discovered by globbing
the directory. Schema: `id` (equal to the file stem), `title`, `exit_criterion`, `order` (sparse
integer; cross-milestone sequence comes from it, not from dependency edges).

<a id="config"></a>
### 6.6 Config

```yaml
# .tracker/config.yml
points_per_week: 5.0
project_start: 2026-10-13
stale_after_minutes: 15
write_pause_seconds: 1.0       # pause between GitHub mutations
repos:
  web-app:     { path: ".", gh: "example-org/web-app" }
  billing-api: { path: "../billing-api", gh: "example-org/billing-api" }
lanes: [api, frontend, docs, infra]
statuses: [Icebox, Todo, "In Progress", Blocked, Done]
```

`points_per_week`, `project_start`, `repos` and `lanes` are required; the other keys default to the values shown. An unknown key is an error, so a misspelt key fails instead of quietly taking its default. A config that can't be read or doesn't validate exits 2, like a missing one.

<a id="index"></a>
## 7. Index

Rebuilt wholesale, never incrementally. The bound that keeps this acceptable: a full rebuild of 500
items finishes in under one second. Incremental updates are worth building only if a measured
rebuild breaks that bound.

The `dep` table holds GitHub's blocked-by edges, keyed by `node_id` on both ends. Pull fills it from
the `blockedBy` field of the same `gh issue list` call that reads the issues; no item file holds
dependencies.

```sql
CREATE TABLE meta       (key TEXT PRIMARY KEY, value TEXT);          -- fetched_at, schema
CREATE TABLE gh_issue   (node_id TEXT PRIMARY KEY, number INT, repo TEXT, title TEXT,
                         state TEXT, state_reason TEXT, closed_at TEXT, parent_node_id TEXT,
                         sub_total INT, sub_completed INT);
CREATE TABLE gh_label   (node_id TEXT, label TEXT);
CREATE TABLE item       (node_id TEXT PRIMARY KEY, issue INT, repo TEXT, draft INT,
                         estimate INT, priority TEXT, lane TEXT, milestone TEXT,
                         baseline_start TEXT, baseline_finish TEXT, path TEXT);
CREATE TABLE dep        (node_id TEXT, blocked_by_node_id TEXT, blocked_by_state TEXT, blocked_by_url TEXT);   -- from pull: gh issue list --json blockedBy
CREATE VIEW  v_work AS   -- the join every command reads
  SELECT i.*, g.number, g.title, g.state, g.state_reason, g.closed_at, g.parent_node_id,
         g.sub_total, g.sub_completed
  FROM item i LEFT JOIN gh_issue g USING (node_id);
```

<a id="cli"></a>
## 8. CLI

<a id="reads-and-writes"></a>
### 8.1 Reads and writes

Reads are implicit and writes are deliberate. Whether an operation can make a wrong decision sets
which is which:

- Pull is read-only, idempotent and decision-free. Requiring a human to remember it only produces
  stale data, so it runs automatically whenever the index is older than
  `config.stale_after_minutes` (default 15 min). `plan pull` exists for scripting and debugging.
- Reconcile creates files and reports orphans. It has consequences and sometimes needs a
  judgement, so it is explicit and dry by default.

`new` and `set` are immediate, while `freeze` and `reconcile` are dry by default. The first pair
write a value the user just typed, so a confirmation prompt would only add a keystroke to a
decision already made. The second pair write values the tool derived across many items, where a
dry run is the only chance to catch a wrong inference before it is committed. The dividing line is
who chose the value, whatever the number of rows.

<a id="commands"></a>
### 8.2 Commands

Query commands are always safe and refresh the index automatically. The Phase column says when
each command ships (§3); §2 lists what Phase 1 leaves out.

| Command | Does | Phase |
|---|---|---|
| `plan status` | Counts, `needs-triage` list, index age | 1 |
| `plan list [--lane frontend] [--milestone beta] [--ready]` | Filtered items | 1 |
| `plan show 23` | One item: GitHub facts joined with ours | 1 |
| `plan next [--lane L]` | One answer: the single task to start now | 1 |
| `plan ready` | One per lane: the parallel view, for concurrent sessions | 1 |
| `plan why 23` | Why this item is not startable: blocked by, behind a lane head, iced, or unestimated | 1 |
| `plan board` | Terminal lane board, ASCII columns | 1 |
| `plan validate` | The lint. Non-zero exit. Runs in the pre-commit hook and before `freeze` | 1 |

Commands that write a value the user named take effect immediately.

| Command | Does | Phase |
|---|---|---|
| `plan new "title" [--estimate N] [--lane L] [--milestone M] [--draft]` | `gh issue create`, then the file | 1 (`--draft`: 3) |
| `plan set 23 --estimate 3 --lane frontend --priority P0` | Validates, then writes; all or nothing (§8.4) | 1 |
| `plan ice 23` / `plan schedule 23 --milestone beta` | Clear or set the milestone | 1 |

Commands that write what the tool decided are dry by default and need `--apply` to commit.

| Command | Does | Phase |
|---|---|---|
| `plan reconcile [--apply]` | Creates files for untracked issues; sets `Done` on items whose issue closed; reports orphans, drafts and reopened issues still marked `Done` (§6.3) | 1 |
| `plan freeze beta [--apply] [--rebaseline]` | Computes and freezes baselines | 1 |
| `plan mirror [--apply]` | The one write-back: `[N]` into issue titles | 1 |
| `plan push-drafts [--apply]` | Turns drafts into real issues, renames files | 3 |

Maintenance commands:

| Command | Does | Phase |
|---|---|---|
| `plan pull [--repo R] [--fresh]` | Explicit index refresh | 1 |
| `plan reindex` | Rebuild SQLite from the committed files. Always safe, because the index is derived | 1 |
| `plan serve [--port 7420]` | The local web UI, bound to localhost | 2 |
| `plan render` | HTML lane board and timeline into `.tracker/out/` (gitignored) | 2 |

Global flags: `--offline` (never call `gh`; serve stale index with a warning), `--json` (machine
output on every query command), `--repo` (scope to one configured repo).

`plan new` creates the GitHub issue first and writes the file second, the order the architecture
requires ([architecture §8.3](../architecture.md#ordering-rule)):

```
plan new "Retry failed webhook deliveries" --estimate 3 --lane api --milestone beta
  1. gh issue create --repo … --title "[3] …"     → returns #24 and node_id
  2. write .tracker/items/web-app/24.yml with identity + planning fields
  3. one commit
```

Offline, `--draft` writes a file with no issue, and `push-drafts` creates the issue later:

```
plan new "…" --draft     → .tracker/items/web-app/draft-01JA7Z…yml
                             issue: null   node_id: null   draft: true
plan push-drafts         → creates the GitHub issues, renames the files to items/web-app/25.yml
```

<a id="next-ready-why"></a>
### 8.3 next, ready, why

`plan next` selects in this order, which is the whole algorithm:

1. drop anything `Done`, `Icebox`, or `needs-triage`
2. drop anything blocked by an open issue
3. drop anything that is not its lane's head
4. sort by `priority`, then `ordinal`, then issue number
5. print the first

```python
def candidates(items, blocked_by, open_ids):  # plan.py; blocked_by from the index dep table
    return [i for i in items
            if i.status not in ("Done", "Icebox")
            and i.estimate is not None                    # needs-triage excluded
            and not any(b in open_ids for b in blocked_by.get(i.node_id, ()))]

def lane_head(lane_items):
    return sorted(lane_items, key=sort_key)[0]

def sort_key(i):
    return (PRIORITY_ORDER[i.priority], i.ordinal if i.ordinal is not None else 10_000 + i.number, i.number)
```

- **`next`**: `candidates` ∩ lane heads, sorted, take the first. One line, plus duration and what
  it unblocks.
- **`ready`**: one row per lane, showing the head, its estimate and its unmet blockers. This is the
  concurrency answer.
- **`why N`**: the negation. Report every reason in order: not estimated · iced · done · blocked
  by an open issue (naming each) · not the lane head (naming the head). It explains a negative, which a
  chart conveys badly anyway.

```
$ plan next
#14 [3] Retry failed webhook deliveries          lane api        P1
    ready · 5d at 5 pts/week · unblocks #18

$ plan next --lane frontend
#9  [5] Settings page: notification preferences  lane frontend   P2
    ready · 7d · head of lane (3 behind it)

$ plan ready
LANE       TAKE  EST  BLOCKED BY
api        #14   3    —
frontend   #9    5    —
docs       #21   1    —
infra      #6    2    #14 #21

$ plan why 18
#18 not startable
  · blocked by #14 (open), #21 (open)
  · behind lane head #9 in lane frontend
```

All three take `--json`, so an agent can consume them without parsing columns.

`duration_days = max(1, ceil(estimate / points_per_week * 7))`. Elapsed calendar time, with no
weekend exclusion: the idle days are already inside the rate.

<a id="set"></a>
### 8.4 set

`plan set N` edits the tracker-owned fields of one item. It is the command-line alternative to
editing `.tracker/items/<repo>/N.yml` by hand, and it runs the same checks.

| Flag | Writes | Clear with |
|---|---|---|
| `--estimate {1,2,3,5}` | `estimate` | `--estimate none` (the item becomes `needs-triage`) |
| `--priority P0..P3` | `priority` | cannot be cleared; the default is `P2` |
| `--status S` | `status`, any value in `config.statuses` | cannot be cleared |
| `--ordinal N` | `ordinal` | `--ordinal none` |
| `--lane L` | `lane`, which must be in `config.lanes` | `--lane none` (the item becomes `needs-triage`) |

Other fields have their own commands: the milestone through `ice` and `schedule`, the baseline
through `freeze`. GitHub-owned fields (title, state, labels, assignee, parent, dependencies) are
never written by `set`. Dependencies are edited in GitHub, or with
`gh issue edit N --add-blocked-by M` and `--remove-blocked-by M`; the next pull reads them.

**All or nothing.** `set` applies every flag to a copy of the item, then runs every `ERROR` rule in
§9 that concerns this item against that copy, including the rule that looks at other items to judge
it (a parent with children carrying an estimate).
Findings about other items do not block it. If any rule fails, the command writes
nothing, prints every failing rule rather than only the first, and exits 1. If all pass, it writes
the file once. `WARN` findings are printed but do not block the write.

Some consequences of running the full rule set:

- `--status Done` fails while the issue is open, and `--status Icebox` fails while the item has a
  milestone. Use `ice` to move an item to the icebox.
- `--estimate 8` and `--estimate 13` always fail, with the message telling you to split the item.
- Changing `--estimate` leaves the issue title's `[N]` prefix stale until `plan mirror --apply`
  runs. `validate` warns about the mismatch in the meantime.

`set` writes immediately, with no dry run, because the user typed every value (§8.1).

<a id="validation"></a>
## 9. Validation rules

`validate.py` has one function per rule, each returning zero or more findings. Exit 1 if any
`ERROR`.

The cycle rule runs over the blocked-by graph that pull cached in the index. GitHub's `addBlockedBy`
rejects a self-dependency and a cycle between two issues, but accepts a longer cycle: A blocked by
B, B by C, and C by A can all be created (verified against the API on `gh` 2.102.0, 2026-10-11).
Self-dependency needs no rule of its own, and neither does a blocked-by target that does not
exist. A blocker can live in a repo outside `config.repos`, because `gh` accepts an issue URL. Pull
still gets that blocker's number, state and URL in the `blockedBy` field, so `next` and `ready`
know whether it is open, but the blocker has no item and cannot be planned, so `validate` warns.

| Rule | Level | Message |
|---|---|---|
| estimate in {1,2,3,5} | ERROR | `#N estimate 8 is a refusal code, not a size — split it` |
| parent with children has no estimate | ERROR | `#N has N children and an estimate; roll-up would double-count` |
| `lane` in `config.lanes` | ERROR | `#N lane 'x' is not configured` |
| no cycle in the pulled blocked-by graph | ERROR | `cycle: #A -> #B -> #C -> #A` |
| blocker is in a configured repo | WARN | `#N is blocked by owner/repo#M, outside the configured repos` |
| blocked-by is intra-milestone | WARN | `#N is blocked by #M in a different milestone; milestone order already implies it` |
| milestone absent ⟺ status Icebox | ERROR | `#N has no milestone but is not Icebox` |
| `status` in `config.statuses` | ERROR | `#N status 'x' is not configured` |
| status Done ⟺ issue closed | ERROR | `#N is Done but issue #N is open` |
| stored Blocked agrees with blocked-by | WARN | `#N is Blocked but no open issue blocks it` |
| `ordinal` unique within a lane | WARN | `#N and #M share ordinal 200 in lane L` |
| every open issue has an item | ERROR | `#N is not tracked — run reconcile` |
| item resolves to a live issue | ERROR | `#N is an orphan (node_id does not resolve)` |
| title `[N]` matches estimate | WARN | `#N title says 3, estimate is 2 — run mirror` |
| estimate and lane present | WARN | `#N needs triage` |
| baseline frozen for a closed milestone | WARN | — |

<a id="github-interaction"></a>
## 10. GitHub and git interaction

Every call lives in `gh.py` / `git.py`. The complete Phase 1 set:

| Purpose | Call |
|---|---|
| Pull issues and dependencies | `gh issue list --repo R --state all --limit 500 --json number,id,title,state,stateReason,closedAt,labels,blockedBy` |
| Pull parentage | `gh api graphql` over `Issue.parent` / `subIssuesSummary`, batched per repo |
| Create | `gh issue create --repo R --title "[N] T" [--parent P]` |
| Mirror | `gh issue edit N --repo R --title "[N] T"` |
| Actual finish | from `closedAt` in the pull; no extra call |
| Rate limits | one `gh issue list` per repo per pull. Mirror pauses `write_pause_seconds` (default 1) between edits, because GitHub's secondary rate limit counts mutations: 80 content-generating requests a minute and 500 an hour. One a second stays under the first; a run of 500 edits would reach the second |

<a id="testing"></a>
## 11. Testing

- `validate.py` and `plan.py` are pure: fixtures in, findings out. Cycle detection and
  `next` selection get a case each per branch, because these are the two places a bug is silent.
  The cycle cases run against a fixture of a pulled blocked-by graph, including a three-issue
  cycle.
- `gh.py` and `git.py` are mocked by a recorded-output fixture; no network in the suite.
- One end-to-end test over the committed fixture tree asserting `validate` exits 0 and `next`
  returns the expected issue.

<a id="work-breakdown"></a>
## 13. Work breakdown

Phase 1 work is the set of GitHub issues whose *Planning* section names milestone `phase-1`. Their
estimates are the plan. Once this repo tracks itself in `.tracker/` (#25), the item files take
over.
